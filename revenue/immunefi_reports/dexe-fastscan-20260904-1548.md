## Finding: Missing `_disableInitializers()` on GovPool Implementation

### Description

The `GovPool` contract uses OpenZeppelin's upgradeable proxy pattern with an `initializer` modifier on `__GovPool_init()`. While this correctly prevents re-initialization of **proxy instances**, the **implementation contract itself** has no constructor calling `_disableInitializers()`. This means:

1. The implementation contract deployed at its own address retains an uninitialized state.
2. Any external actor can call `__GovPool_init()` directly on the implementation contract address.
3. If the implementation contract holds any native ETH or tokens (e.g., via accidental transfer), an attacker could initialize it and potentially extract those funds using governance functions.

### Affected Contracts

| Contract | File | Has Constructor? | Has `_disableInitializers()`? |
|----------|------|-------------------|-------------------------------|
| GovPool | `contracts/gov/GovPool.sol` | ❌ No | ❌ No |
| GovSettings | `contracts/gov/GovSettings.sol` | ❌ No | ❌ No |
| GovUserKeeper | `contracts/gov/GovUserKeeper.sol` | ❌ No | ❌ No |
| GovValidators | `contracts/gov/GovValidators.sol` | ❌ No | ❌ No |

This pattern is inconsistent across the entire governance suite — **none** of the core gov contracts disable initializers on the implementation.

### Root Cause

OpenZeppelin's [upgradeable contract documentation](https://docs.openzeppelin.com/upgrades-plugins/1.x/writing-upgradeable#initializing_the_implementation_contract) explicitly recommends:

```solidity
constructor() {
    _disableInitializers();
}
```

This prevents the implementation contract from being initialized outside of a proxy context. DeXe Protocol omits this safeguard entirely.

### Why This Is Not Critical

1. **No funds at implementation addresses**: DeXe deploys via `PoolFactory`, which creates proxies. The implementation contracts are deployed once and never receive user funds.
2. **Proxy instances are safe**: Each proxy has its own storage slot for `_initialized`, so the `initializer` modifier works correctly per-proxy.
3. **No ownership escalation on proxies**: Initializing the implementation does NOT affect any existing proxy instance.
4. **Known pattern**: Many protocols omit this without incident, though best practice dictates including it.

### Recommended Fix

Add a constructor to each upgradeable governance contract:

```diff
 contract GovPool is
     IGovPool,
     AbstractDependant,
     ERC721HolderUpgradeable,
     ERC1155HolderUpgradeable,
     Multicall,
     BlockGuard
 {
+    /// @custom:oz-upgrades-unsafe-allow constructor
+    constructor() {
+        _disableInitializers();
+    }
+
     using MathHelper for uint256;
```

Apply the same pattern to `GovSettings`, `GovUserKeeper`, `GovValidators`, `ERC721Expert`, and `ERC721Multiplier`.

## False Positive Clarification: Scanner Finding at Line 115

The automated scanner flagged `__GovPool_init` at line 115 as "access-control-missing." This is a **false positive** because:

- The `initializer` modifier IS present (line 122) and functional.
- It is inherited through `ERC721HolderUpgradeable → Initializable` (OZ contracts-upgradeable v4.9.2).
- The modifier enforces single-use initialization per proxy instance via OZ's `_initialized` storage slot.
- The function is correctly called only by `PoolFactory.sol:285` during pool creation.
